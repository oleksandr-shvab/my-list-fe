# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is the frontend of Daily Game Challenge. Auth (register/login/logout) is the first real feature, built on TanStack Router + TanStack Query + Zustand + axios (see Stack below). Unit tests run on Vitest (`npm test`; config in `vitest.config.ts`, files named `*.test.ts` next to the code). CI (`.github/workflows/ci.yml`) runs lint, format check, type check and build, and the tests. Component tests run in jsdom with Testing Library (see Conventions). There are no end-to-end tests yet.

- `npm run build` — type-check via `tsc -b` then produce a production build with `vite build`
- `npm run lint` — run ESLint over the project
- `npm run format` — format the project with Prettier (`npm run format:check` only checks)

## Architecture

- Entry point [src/main.tsx](src/main.tsx) builds the `QueryClient` ([src/lib/query-client.ts](src/lib/query-client.ts)) and the router ([src/router.ts](src/router.ts)), installs the session guard, then mounts `RouterProvider` (wrapped in `QueryClientProvider`) into `#root` in [index.html](index.html). Both are factory functions, so tests can build their own. There is no top-level `App.tsx` — routes under `src/routes/` own what renders.
- Static assets served as-is live in [public/](public/) (today only the favicon).
- TypeScript project uses solution-style config: [tsconfig.json](tsconfig.json) references [tsconfig.app.json](tsconfig.app.json) (app source, `src/`) and [tsconfig.node.json](tsconfig.node.json) (Vite config itself). `tsc -b` builds both as part of `npm run build`.
- ESLint config ([eslint.config.js](eslint.config.js)) is flat-config style, composing `@eslint/js`, `typescript-eslint`, `eslint-plugin-react-hooks`, and `eslint-plugin-react-refresh`. It currently uses non-type-aware TS linting (`tseslint.configs.recommended`), not the stricter type-checked variants.

## This repo

Frontend only. It talks to the FastAPI backend in the `my-list-be` repo, on `http://localhost:8000` in dev.
The app calls `/api/v1/...`; Vite's dev proxy (`vite.config.ts`) strips `/api` and forwards `/v1/...` to the backend.
Open the app at `http://localhost:5173`, not `127.0.0.1`, because the session cookie is host-scoped.
The dev proxy keeps the browser's `Origin`; do not rewrite it. `127.0.0.1:5173` and the preview server on `4173` are not allowed origins, so their POSTs get 403.

## Stack

- Vite + React + TypeScript
- **TanStack Router** (file-based, routes in `src/routes/`) — not React Router
- **TanStack Query** for all server state
- **Zustand** for client-only state (the theme today) — keep this minimal, most state should be server state via Query, not client state. The signed-in state is server state: it is not in Zustand.
- **axios** for HTTP — one shared instance in `src/lib/api-client.ts` (`baseURL: '/api'`, `withCredentials: true`), with a response interceptor that normalizes every failure into a typed `ApiError`
- Tailwind CSS v4 (no config file — `@import "tailwindcss"` in `index.css`) + shadcn/ui — installed; `components.json` uses the `radix-nova` style/preset (Radix UI primitives, `neutral` base color). Add components with `npx shadcn@latest add <name>`, which lands in `src/components/ui/` (treat as vendored — don't hand-edit beyond what the CLI generates; the edits listed under "Vendored edits" below are the only ones). `cn()` helper lives at `src/lib/utils.ts`. Note: this registry's `form` item resolves to zero files — there is no classic RHF-context `Form`/`FormField` component here. Build forms with the newer `Field`/`FieldLabel`/`FieldError`/`FieldGroup` primitives (`npx shadcn add field`) wired directly to `react-hook-form`'s `register()`/`formState.errors`, no context wrapper needed.
- Zod + React Hook Form for forms — installed (`zod`, `react-hook-form`, `@hookform/resolvers`)

## Key architectural decisions

- **API types and client**: generated from the backend's OpenAPI snapshot with Orval (`npm run api:generate`, config in `orval.config.ts`; locally it reads `../my-list-be/openapi/openapi.json`, CI reads the snapshot on the backend's `main`). The output is committed in `src/api/generated/` (never hand-edit it) and every request goes through `apiClient` via `src/lib/orval-mutator.ts`, so errors become `ApiError`. `src/features/auth/types.ts` only aliases the generated models. CI's `api-types` job fails when the committed code differs from the backend contract. Backend paths are under `/v1`, so the app calls `/api/v1/...`.
- **Auth**: Session-cookie auth (Django-auth style), not JWT. The backend sets an httpOnly `session_id` cookie on login and register (register logs in too). The frontend never handles a token; all requests use the shared axios instance with `withCredentials: true`. Login is optional: the `_app` layout and its pages are public, and only the pages under `src/routes/_app/_account/` (today `/profile`) need an account. The backend refuses any request other than GET, HEAD or OPTIONS (in practice POST, PUT, PATCH and DELETE) whose `Origin` (or `Referer`, when `Origin` is absent) is not exactly an allowed origin (403 `csrf_origin_mismatch`), and any POST, PUT or PATCH with a body that is not JSON (415 `unsupported_media_type`). The frontend needs nothing for it, since browsers send `Origin` on its requests. There is no custom CSRF header, by decision (SPEC-02 Q18).
  - **One source of truth.** The signed-in state lives only in the `GET /auth/me` query (`meQueryOptions`). Its data is the user, or `null` for a guest (`getMe` turns a 401 into `null`). A query error means "unknown" (network, 5xx). Nothing copies it into other state. Read it with `useSession()` (`src/features/auth/session.ts`): status `pending`, `signed_in`, `guest` or `error`, plus `user` and `retry`. Route guards call `ensureSession(queryClient)`.
  - **Guards.** The root route starts `/auth/me` and does not wait, so public pages show at once. `_app/_account.tsx` waits for it: a guest goes to `/login?redirect=<page>`, and a failed check shows the error screen with the request id inside the layout. Login, sign-up and forgot-password wait too and send a signed-in user to `/`; if the check fails they show anyway. Reset-password does not wait and keeps its token for a signed-in user. These guards are a convenience: the backend answers 401 on account endpoints either way.
  - **`redirect` search parameter.** Anyone can write it into a link. `resolveRedirect` (`src/features/auth/redirect.ts`) accepts only the site's own origin, returns the resolved path, query and hash, and rejects the auth pages and paths that start with `//`. Never navigate to the raw value.
  - **401 mid-session.** `installSessionGuard` (`session-guard.ts`) reacts to a 401 on any call while a user is shown: it sets the `me` data to `null` and drops all other cached queries (`signOutLocally`). On an `accountOnly` page it also shows the "session ended" toast and invalidates the router, so `_account` sends the user to login. A game response whose top-level `signed_in` is exactly `false` has the same effect while a user is shown, through the same interceptor. "Game response" means the request really went to this site's API under `/v1/games/` (`apiPathOf` in `api-client.ts` resolves `baseURL` and `url` together; a `baseURL` with or without a trailing slash is the same); a nested field, a string, `null`, an array or a Blob never counts. The response always reaches its caller unchanged, and a failure inside the guard is reported, never thrown. Only an answer to a request sent in the current session counts: the guard stamps each request with `getSessionEpoch()` (`session.ts`), so a request sent as a guest and answered after a login, or sent before a re-login and answered 401 after it, leaves the new session alone. The epoch is raised by one subscription to the `me` data whenever the user's id changes (null to user, user to null, user A to user B), and by `onAuthSuccess`, because a re-login as the same user changes no id. `ApiError` keeps only the stamp (`sentInEpoch`), never the request, whose body can hold a password. While a logout runs (`setLogoutRunning`) no answer ends the session, so a late 401 shows no "session ended" toast. On a public page the user stays. `getMe` passes the query's abort signal, so a `/auth/me` request that a login or logout replaced is dropped and its late 401 cannot sign the new user out. Do not use `queryClient.clear()` or remove the `me` query to sign out: a mounted `useQuery` keeps reading the removed query and shows the old user.
  - **Logout and reset.** `finishLogout` signs out locally and goes to `/` only from an account page. `finishPasswordReset` signs out locally and goes to `/login`, because the backend ends all sessions of the reset account.

## Games

- The registry is `src/features/games/registry.ts`, a static list of the games the frontend can open. The backend lists the enabled ones (`GET /v1/games`, `src/features/games/queries.ts`: query key `['games']`, 5 minutes fresh, no retry), and the nav, `/` and `/games/$slug` use only the games both sides know (`src/features/games/known-games.ts`). Backend slugs the registry lacks are ignored. When the call fails, the registry alone decides, so the app works with the list down. An entry has exactly five items: `slug`, `nameKey`, `order`, `isDefault`, `screen` (`src/features/games/types.ts`). Adding a game is adding one entry.
- Exactly one entry is the default, and `/` shows it. Slugs match `^[a-z0-9]+(-[a-z0-9]+)*$` and are unique, and every `nameKey` exists in both catalogues. `validateRegistry` checks this; `validate-registry.test.ts` runs it on the real registry.
- The shell gives a screen only `slug` and `date`: a YYYY-MM-DD UTC day from the address, or `null` on today's pages (`/` and `/games/$slug`). A screen asks the server for today and takes the date from the answer; whether a puzzle is today's comes from the server's clock, never from a flag the shell computes. A screen is a lazy component, so a game's code downloads when its page opens.
- `GameScreen` (`src/features/games/game-screen.tsx`) renders the screen inside `GameErrorBoundary` and a `Suspense`. A crash shows an error with "Try again" inside the layout, and the sidebar keeps working. The boundary is keyed by game and day, never by language, so a language switch keeps the screen and its state. A game module must not key its progress by language either.
- `src/lib/utc-date.ts` formats UTC days and checks the shape of a date from the address. The device's clock never decides what is visible. The clock hook (`src/features/clock/clock.ts`, `useServerClock`) returns the server's today, the next reset and the offset from `GET /v1/clock` (query `['clock']`, no retry, refetched when the page becomes visible); when the call fails it falls back to the device's UTC day.
- The game guesser's view is `['game-view', slug, date, viewer]` (`src/features/games/view-queries.ts`): one key per puzzle day and viewer, whichever address opened it, so `/` and `/games/$slug/$date` show the same cached game. `viewer` is the user id, `'guest'` (the session check said guest) or `'unconfirmed'` (the check failed: the page does not know). The query waits for the session check, and a sign-in or sign-out changes the key by itself. Never read a view as a guest's from its key: trust the view's own `signed_in`. A guest's view is built by `loadView` (`view-queries.ts`): with a stored game it is resume with the record's guesses and the empty view is never fetched (AC-39). A page with no date asks `/today` first; when its answer says `signed_in: false` (whoever the page thinks is signed in, as a session may have ended) and the browser has a stored game for that day, the today query writes no view (it only keeps the answer's `daily_proof` in the record) and the dated query of the pinned day resumes it, so a failed resume is that query's error and its "Try again" resumes again without asking `/today`. A 422 `invalid_guess_history` on resume drops the record, shows a toast with `games.progress_damaged` and shows the fresh view (AC-42). `errors.invalid_guess_history` keeps its general text: the merge route returns that code too. `'guest'` can briefly hold an account's view after a login in another tab.
- A page with no date (`date === null`) first asks `/today` through `['game-today', slug, viewer, opening]`, writes the answer under its day's key, and the screen pins that day in its own state. Every later fetch of that page (a refetch, a retry, a new viewer) asks for the pinned day by its date, never for "today" again (AC-47). `opening` is a `useId` per screen shown, and `GameScreen` is keyed by `nextOpening()` (`openings.ts`), which the two today routes take in `beforeLoad`. So a player's visit to a today page, also a link to the page they are on, asks for today again, and a refetch or a tab focus never does. This is the seam for the day-change message (M1-32 step 7): "Play today's puzzle" can be an ordinary link to the today route.
- A guess (`guess.ts`) writes the answer into the key the page reads, except that `signed_in: false` goes to `'guest'` and `signed_in: true` never goes to `'guest'`, from inside `mutationFn`, so a sign-out mid-game finds the answer already in the guest key. An answer or a fetched view that says `signed_in: true` while the page is not sure (`'guest'` or `'unconfirmed'`) asks `/auth/me` again (`refreshSession`), as a sign-in. After a network error, 409 `puzzle_already_finished` or 422 `duplicate_guess`, the view is fetched again before the message shows, when the shown view says `signed_in: true` (the server holds that game); nothing is refetched after a network error for a guest, whose game lives in the browser. A guest's 409 or `duplicate_guess` refetches only when the record has guesses and differs from the shown game (guesses or status), which resumes from it (another tab played, AC-43, AC-46); with no record the empty view would wipe the screen. A record whose status is not `in_progress` is never sent as `previous` (a lost game is six guesses, more than a guess may carry): the guess is not sent, the view is resumed from the record and the status line says the puzzle is finished. A guest's 422 `invalid_guess_history` drops the record and refetches the fresh view, unless the record is a finished game (then it is resumed and kept); the status line shows `games.progress_damaged`, with no toast. Where a view lives is one rule, `viewTargetOf` (`view-queries.ts`), used by `writeAnswer`, `useGuess` and `useRefreshLinks`: a view that says `signed_in: false` lives under `'guest'` (`'unconfirmed'` stays), an account's view never under `'guest'`. On a page whose viewer is a user id a guest view can only appear after the session guard has signed the page out, so the screen reads that key next; the case has no test because the guard makes it unreachable. A guess that gets a 422 for a history another tab replaced resumes and keeps the new record, and the status line says `games.game_changed`; a resume that gets such a 422 resumes the newer record once. A guess reads the record once, also for a signed-in view, so an answer that turns out to be a guest's (AC-52) keeps the stored proof and flag.
- The archive marker (AC-88) shows when the view says `counts_for_streak: false`, or when it is `null` and the server's today (`useServerClock().source === 'server'`, never the device fallback) is later than the puzzle's date. A page that opened as today never shows it. A clue link stays while it is the same file, unexpired and not failed (`clue-media.tsx`), because each guess signs every link again.
- A clue file that fails (an image, a clip's last `<source>` or the `<video>` itself) asks for fresh links once (`clue-media.tsx`, `useRefreshLinks` in `refresh-links.ts`). For a view that says `signed_in: true` it fetches the dated view again; for a guest's it runs `loadView` (resume from the record, the shown guesses when there is no record, the same 422 handling) and drops that answer if a guess was answered meanwhile. The request resolves with the steps, and `ClueMedia` takes its step's media from that answer; it never compares links with the cache, which reaches it later. A second failure shows "The clue didn't load." with "Try again", and nothing asks again until the player presses it; "Try again" takes the media off the page until the answer comes. A guess's link set replaces the shown links only when they failed, expired or are another file, and only then starts fresh: links that were asked for stay on trial otherwise.
- A clip's poster has its own state: a poster that fails asks for links once and takes only the new poster (the clip is not touched or restarted), and if that fails too the poster is dropped, with no failure shown. A poster that ran out is replaced by a guess's, again without touching the clip. The clip's loading state ends on its first frame (`loadeddata`) or when the poster has loaded.
- The step-6 clip (`clue-video.tsx`) is muted, looping and inline, and has a play and pause button always. It starts with `play()` unless `prefers-reduced-motion: reduce`. A clip on a step that is not selected (`active` false; earned steps stay mounted) pauses and plays again when shown if it was playing, or if it never started and nothing stops it. A failure on a hidden step waits until the player opens it. New links make it load again and play on the same terms.
- One function, `withKnownValues` (`guest-progress.ts`), keeps a guest's `counts_for_streak` and `daily_proof` from going null (resume, later guesses and a view off the puzzle's own day send null): it takes the answer and the sources to fall back on (the record, the cached view; the first non-null wins). `loadView`, the today query and `writeAnswer` all use it, so a plain view, today, resume, guess and a clue refresh behave alike.
- **Guest records** (`guest-records.ts`, policy in `guest-progress.ts`): one `localStorage` key per game, variant and day, `dgc.guest.v1.<slug>.<variant>.<date>` (the variant is the constant `DEFAULT_VARIANT`, `default`, because the app never asks for another). A record is `{ guesses: { title_id, name, result }[], status, counts_for_streak, daily_proof }`: no answer, no media link, nothing by language. A Zod schema checks every read, and a bad shape or non-JSON reads as no record (it is left in place until the next write). Records are written only from answers that say `signed_in: false`: after a guess the record is the answer's whole guess list (not the old record plus one), and a view, today or resume only keep a non-null `daily_proof`. `counts_for_streak` is the first guess's and a later null never replaces it; a non-null `daily_proof` is never erased. A resume answer gets the record's two values back (`withStoredValues`). When the browser throws on any storage call, the record is kept in a map of the tab (it wins over the storage, a deleted record is a `null` in it) and a toast says once that the game lasts until the tab closes (AC-44). Records stay until merged (Q7). `readGuestRecords(slug)` lists only records with at least one guess: a record that only keeps a `daily_proof` (a view seen, nothing guessed) is for `readGuestRecord`, so stats, archive and merge never count an unplayed day. The answer to a guess is stored before the view cache gets it (AC-41), so a reload straight after shows the same state. A guess sends the record's guesses as `previous` read at send time (`previousOf`), for an account the shown ones (AC-38, AC-51). Each action reads the record once and passes it down (`recordGuestAnswer` takes it, `null` for none). There is no `storage` event listener: a second tab catches up on its next guess or reload.
- **Midnight** (`use-day-change.ts`): a page with no date in its address keeps its puzzle (AC-47). `useDayChange(openedDate)` says when the server's day, taken from the clock offset at the moment of the check, is later than that puzzle's; it decides only with the server's clock (`source === 'server'`; the device's fallback never says a new day has started), and checks when the tab becomes visible. `check()` is for a submit (`useGuess` takes it as `onSend`, run just before a request is sent, not for a press that sends nothing) and for the M1-33 countdown when it reaches zero. The message has a "Play today's puzzle" link to `/games/$slug`: an ordinary visit to a today route, which asks `/today` again (`openings.ts`); the day-keyed views need no invalidation.
- Routes: `/` (the default game, today), `/games/$slug` (today), `/games/$slug/$date` and `/games/$slug/archive`. `games/$slug.tsx` checks the slug against the registry (exact and case-sensitive) and then against the backend's list, and `$date.tsx` checks the date. `/` checks the default game against the list the same way. A bad slug or date, or a game the list lacks, throws `notFound()`; `/` and `$slug` show "Unknown game", and the "not found" screen renders inside the layout. Today's date shows the same screen as `/games/$slug`, with no redirect. `$date.tsx` checks only that the date is a real day; a future, pre-launch or missing puzzle is the backend's 404 `puzzle_not_found`, which the screen shows as "No puzzle for this date" inside the layout.
- The title search (`game-guesser/title-search.tsx`, `title-queries.ts`) is a hand-built combobox (ARIA authoring practices: the focus stays in the input, `aria-activedescendant` names the option, the list is in the page). The list is the server's, in the server's order, and nothing filters or sorts it. The query key is `['titles', slug, q]` with the trimmed text after a 250 ms pause, no `placeholderData`, no retry, and no refetch on window focus or reconnect, so an answer can show only for its own text and a refused search (429, 403) is never sent again by itself. Nothing is asked until the text has settled (equals the debounced text; a text that already has an answer settles at once and shows no "Loading…"), never for a pick's name until the player edits the text (also after a 422 clears the pick), and not at all for a text with fewer than 2 letters or digits (`\p{L}\p{N}`, as the server gives nothing for "a."). The listbox exists only while it has options: a message (too short, loading, empty, failed) is linked to the box with `aria-describedby` and the box is not expanded. Up from no highlight goes to the last option, Down to the first, and the highlighted option is scrolled into view when the list opens or its items change. The result count is announced after a short pause, the region empty before, so the same count for another text is heard again. A search that fails with a 4xx shows that code's catalogue text (`getErrorMessage` with the fallback `games.search.failed`); a 5xx or network failure shows "Search failed. Try again.". A key press during an IME composition is ignored. A guess answered late clears the box and the pick only if the pick is still the title that was sent. A picked title is sent by id through `useGuess`, never as text. After 422 `duplicate_guess` or `title_not_found` the pick is cleared; after any other failure (429 included) it stays and Guess works again at once.
- The game guesser's screen is `src/features/games/game-guesser/game-guesser-screen.tsx`; its clue steps are the reusable `src/features/games/clue-ladder/`, which reads the step count from the view. The registry entry still has exactly five items.

## Shell

- Every page under the `_app` layout (`src/routes/_app.tsx`) has the same frame: a skip link (`src/components/skip-link.tsx`, the first focusable element, it moves focus to `main`), the sidebar, and one `main` (id `main`, `tabIndex` -1) that holds the page. The layout does not use `SidebarInset`, so the phone header is not inside `main`.
- The sidebar (`src/components/app-sidebar.tsx`) holds, in this order: the brand link, a `nav` labelled "Games" with one entry per known game (in `order`) and the archive link (for the current game, else the default game if known, else the first known game; no link when no game is known), then at the bottom the language switcher, the theme toggle, the account area and the collapse button. It stays open beside the content from 768 px and keeps its icon-collapse mode and the `sidebar_state` cookie.
- The current game (`src/features/games/use-current-game.ts`) is the game of the `slug` in the address, or the default game on `/`. Exactly one game entry gets `aria-current="page"`, and none on the archive page (the archive link has it) or on pages that are not a game. The entry sets the attribute itself, because `activeOptions.exact` stops the router marking it on the archive page and does not match `/` or a dated page.
- Below 768 px `PhoneHeader` (`src/components/phone-header.tsx`) shows one row: the sidebar button, the brand and the compact account control. It is the page banner, and sticks to the top only on screens at least 500 px tall. `src/index.css` adds `scroll-padding-top` so it never covers the focused element. The sidebar becomes a panel (a Radix dialog). It is opened by a plain button, not a dialog trigger, so Radix cannot return focus; `PhoneHeader` focuses its button when the panel closes without navigation (Escape, a tap outside, the close button), and `main` when a link in the panel closed it (the sidebar's links set a ref the layout shares). The phone breakpoint is `not (min-width: 48rem)`, the exact complement of Tailwind's `md`, in `use-mobile.ts` and in the `index.css` media query. Wider screens do not render the header at all, and the collapse button shows only there.
- The account area (`src/features/auth/components/account-area.tsx`) has a `sidebar` and a `compact` variant. Its states are a placeholder of the same size, "Retry", "Log in" and "Sign up" (each carrying the current page as `redirect`), and for a signed-in user a dropdown menu (Profile, Log out) whose button is named with the email. While a logout runs, the button is `aria-disabled` (never `disabled`, which drops the focus), ignores the open keys, and is busy and named "Logging out…" (the menu closes on select), and afterwards the focus moves to "Log in". Choosing Profile in the panel focuses `main` once the menu is gone (the menu's own focus return is skipped). The sidebar's links close the phone panel only on a plain click (`src/lib/plain-click.ts`); a ctrl, cmd, shift, alt or non-primary click is left to the browser.
- Touch controls are 44 px high below 768 px (`max-md:` classes on our own components), and at least 24 px everywhere.

## Conventions

- Routes: one file per route under `src/routes/`, file-based. `routeTree.gen.ts` is auto-generated on `npm run dev` — never hand-edit it. After you add, move or delete a route file, run `npx vite build` first: `tsc -b` fails on a stale tree.
- Page titles: a page route sets `staticData: { pageTitle: '<catalogue key>' }`. `useDocumentTitle` (`src/lib/page-title.ts`) shows it as "{page} | {app name}" and follows the language. A game page sets `GAME_NAME_TITLE` instead, which becomes the name of the game in the `slug` param (the default game on `/`). An unknown path falls to `src/routes/_app/$.tsx`, so the "not found" screen stays inside the layout.
- Tests: `*.test.ts` next to the code. Router tests are in `src/test/`: they build the real route tree from `src/router.ts` on a memory history, with a fake backend behind the axios client (`router-harness.ts`), and run in Node. Import `src/test/browser-stubs.ts` first in such a file. Never put a test file in `src/routes/`: the router plugin would treat it as a route. A test that needs a stylesheet's text gets it from `vitest.config.ts` through `provide` and `inject('cssText')` (typed in `src/test/provided-context.d.ts`): `?raw` returns an empty string for CSS, and importing `node:fs` in `src/` would leak Node types into the app type check.
- Component tests: the first line is `// @vitest-environment jsdom` (Node stays the default), and `src/test/dom-setup.ts` is the first import (a `matchMedia` stub and Testing Library cleanup; there is no `scrollIntoView` stub, the sidebar scrolls its own list). `src/test/app.test.tsx` and `src/test/shell.test.tsx` render the real route tree in jsdom with the same fake backend (the shell tests cover the current-game mark, the account menu keys, the skip link, the landmarks and the phone panel; `vi.stubGlobal('matchMedia', …)` makes the screen a phone); hook tests use `renderHook` with `RouterContextProvider`. Query by role and text and use `userEvent`. `jest-dom` is not installed, so assertions are plain (`textContent`, `getAttribute`).
- Path alias `@/` → `src/` (configured in `vite.config.ts` and the `paths` field of both `tsconfig.json` and `tsconfig.app.json`; no `baseUrl` — deprecated in the TS version this project pins)
- Anything that touches the API goes through TanStack Query; Zustand only for state with no server counterpart
- Client-side validation (Zod) is a UX convenience, not a security boundary — the backend re-validates everything regardless
- Comments: only when the why isn't obvious from the code, 1-2 sentences max

## Translations (English and Russian)

- react-i18next, set up in `src/i18n/` (imported first in `main.tsx`). Texts live in `src/i18n/locales/en.json` and `ru.json`; keys are typed from the English file, so `t('auth.login.title')` is checked by `tsc`. A Vitest test fails when the two files have different keys (plural suffixes aside).
- Never write user-visible text in a component: add a key to both catalogues. Russian plurals need `_one`, `_few`, `_many`, `_other` forms and a `count` param.
- The language is chosen by: the saved choice (`localStorage` key `language`), else the browser's language if it is English or Russian, else English (`src/i18n/language.ts`). `<html lang>` follows. The language switcher is `src/components/language-switcher.tsx`. Saving it on the account comes with a backend field later.
- Backend errors are translated by `code`: `errors.<code>` in the catalogues (`src/lib/error-messages.ts`); an unknown code shows `errors.unknown`, never the backend's English. Zod schemas are built with the current `t` (`createLoginSchema(t)` in `useMemo`).
- Errors: unexpected errors go through `src/lib/report-error.ts` (the future error tracker hook); Query retries only network errors, 5xx, 408 and 429, at most twice (`src/lib/query-retry.ts`); an old tab that fails to load a lazy chunk after a deploy reloads once (`src/lib/version-skew.ts`).
